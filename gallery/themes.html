A theme owns structure, not just colour

This is the whole thesis, so it goes first. Almost everywhere else, "theme" means a palette: swap the tokens on a sidebar-and-cards dashboard and you get the same dashboard in a different colour. That fails the moment someone dislikes the shape of a product — and the shape is usually what they meant. A token swap cannot reach composition.

Here a theme also chooses how components draw themselves, where navigation lives, how dense the spacing and type ramps are, whether a grid is painted behind the stage, and whether items carry numbers. Terminal deletes every box in the product. Blueprint numbers every item and moves the navigation into a drafting title block. Same screens, same markup, and no screen aware that any of it happened.

layerwhatwho owns it
L0palette Private literals, --_ prefixed. The only place a hex is legal — which is what makes the lint rule one sentence: a hex outside a theme file or the L0 block is a violation.
L1roles Semantic tokens, --i- prefixed. The only thing components consume. A component that needs a new literal means the system is missing a role.
L2structure How components draw and where the shell puts things. Scalars are --x- custom properties; discrete modes are data-* attributes with their rules in contract.css.

Everything hangs off one attribute, data-theme. applyTheme() writes it together with every structural attribute it implies, in a single pass, so a half-applied theme is impossible — the failure where the palette switches but the layout doesn't is exactly what makes theming feel broken. It also writes color-scheme rather than each theme declaring its own: there is exactly one global declaration in the codebase, and a second one anywhere would silently win for its subtree and desync the themes. A light-only theme still states its scheme inside its own block, so the stock is right before any JavaScript has run.

…and four things it may never do

The freedom above only stays safe because of these. A change that breaks one is the wrong change, not a case for relaxing the rule.

1 Never change what a role means. --i-crit is "this failed" in every theme, forever. A theme picks the hue; it does not get to repurpose the role. This single rule is why themes swap without auditing every screen.
2 Never target a view. A selector naming an app class means the theme is patching a screen instead of expressing itself through the system. Themes target .i-* only.
3 Contrast is not negotiable. Body text clears 4.5:1 against its own surface in every theme, light and dark. Computed, never eyeballed — each theme file records its measurements in its header.
4 One color-scheme declaration. A light-only theme writes color-scheme: light inside its own block; it does not add a second global.

Depth has no box-shadow anywhere in the system: it is translucency plus a hairline plus the page wash showing through, which is why dark themes stay crisp instead of turning to mud. Terminal's one box-shadow is a zero-blur 1px ring drawn on a cell — a hairline with a spread, not depth — and its file says so.

The six themes

Generated from the THEMES array in src/themes.js — rows and columns both. The column list is the union of the registry objects' own keys, so a new structure axis appears here the day it is added to a theme, and this table cannot drift from what the product actually applies. Nothing in that registry is a colour; colours are the theme CSS file's job, always.

Values sitting at the contract's own default are dimmed, so what remains is what each theme actively spends. shell and scheme have no default and are never dimmed.

Note surface: none on Terminal — dimmed nowhere, because "none" is that theme's loudest decision rather than an unspent axis.

Colour roles, all six themes at once

Every theme down one axis, every role across. Roles, not colours: signal means "this wants you, or binds you", machine means "the system is speaking", crit and ok are outcomes. Because a role can never change meaning, a column is a single claim rendered six ways — and a theme that had quietly repurposed one would show up here as a swatch that doesn't belong in its column.

Three things are worth reading off it. Crit is the only role that is a hue in all six themes — failure is the one claim nobody spends on anything else; Blueprint goes further and reserves red entirely, so seeing it at all means something faulted. Signal is not a colour in two of them. Blueprint sets it to the hard object line, because a drawing signals with line weight rather than hue; Swiss sets it to ink, because on paper the strongest possible mark is the attention — and a theme that spends colour on attention has none left for alarm. Ok is graphite in those same two: a drawing sheet calls a passing item "nominal" and draws it in plain lead, and on Swiss "it worked" is not news.

Five of these rows simply set data-theme on themselves, which works because every theme file scopes its tokens to [data-theme=…] as an ancestor selector rather than to :root. Instrument is the exception and the exception is informative: the house theme has no such block, because it is the :root fallback every other theme overrides — so its row is read from :root at load rather than restated here. It is also the only dual-scheme theme in the set, so that row renders in your system's preferred scheme while the other five are fixed light or fixed dark.

The six shell layouts

The shell is the one place structure genuinely branches, and it branches once. A left sidebar, a bottom status bar and a drafting title block are not the same DOM, and clever CSS pretending otherwise is a compromise in all three — so this is real markup chosen by variant, while everything else in the system stays cascade. Adding a variant touches no view. Each diagram below is built from divs; the pale block is the stage.

sidebar

The house default. A 2px rail marks the active route — the same rail the agent trace uses, so "you are here" and "a machine did this" are one visual idea.

topnav

No side column at all. A two-tier rule — identity above, destinations spread across the full measure below — so the page starts at the very top of the field.

rail

A narrow metadata column set in the human voice, lowercase, with the active item marked by a short dash rather than a filled block.

statusbar

The TUI. A command line pinned above, a fixed status bar below carrying the destinations as numbered keys, and uninterrupted field between them.

topbar

The bar is itself a tile, floating on the field with everything else. Bento's rule that nothing is furniture: navigation is one more object in the composition.

titleblock

The drafting sheet, and the only variant where the stage comes first in the DOM. Notes at the top of the right column, the title block anchored at its foot carrying the sheet index; destinations are sheet numbers.

Every variant collapses to a stacked page below 60rem rather than a squeezed one — that collapse rule is part of adding a variant, not an afterthought.

The structure axes

The L2 contract: what a theme may set beyond colour. Every one of these got here the same way — a theme needed something it could not express and was brute-forcing around it, so the contract was short a dimension. Not one was designed up front, and the changelog records which theme asked for each, which is what stops the list growing on speculation. A theme that needs something not on this list is telling you to add an axis, not to write a one-off rule.

axiskindvalues what it solves
--i-mono · --i-prose scalarfont stacks The two voices: mono is the machine, prose is the human. That split carries most of the identity and survives having no web fonts — assume there are none, and lean on the one contrast system stacks reliably give you.
--i-display-face scalardefaults to --i-mono The figure and page-title face, for a theme whose display voice is not the machine voice.
--i-chrome-face scalardefaults to --i-mono Card titles, row titles, buttons, tags and table heads. Split out because those were hardwired to mono, so a serif or grotesque theme had to restate the same idea at six selectors.
--x-label-case scalarnone · uppercase How micro-labels are set — eyebrows, stat labels, field labels, kv keys, table heads.
--x-label-track scalarletter-spacing Tracking for those same labels. Wide tracking is most of what makes a caps label read as furniture rather than as text.
--x-figure scalar2.6rem Display-numeral size, and the single biggest lever on how a theme feels. It is a ceiling: each stat is its own query container and the figure resolves to min(--x-figure, 18cqi), so the column it actually got imposes the real limit. Before that, figure and grid floor were two numbers that had to agree by hand and didn't — a theme raised its figure and a long value ran across its neighbour.
--x-title scalardefaults to --i-h1 Page-title size, sibling to the figure. Themes disagree about titles as much as about figures, and pinning it made every theme open its page the same way.
surface modetile · outline · rule · none How every container-drawing component draws itself. Written once against a shared selector in the component layer — see the demo above.
shell mode sidebar · topnav · rail · statusbar · topbar · titleblock Where navigation lives. Real DOM, so it is the one component variant rather than a CSS mode.
--x-stat-floor scalar8rem Minimum stat column width. Floors come from CONTENT — a stat is a short number plus a short label — never from how many items one screen happens to pass. A theme that raises the figure must raise this with it, or the container clamp quietly shrinks the numeral back down.
--x-card-floor scalar13rem Minimum card column width — larger, because a card carries a sentence. Tuning a floor so this screen's six items fit one row breaks the next screen's four.
--x-hero mode0 · 1 The first stat spans 2×2 and carries the loudest number. Bento's rule that nothing is the same size as anything else — composition as hierarchy, expressed once.
--x-radius scalar10px Corner radius for tiles; the small and pill radii derive from it, so 0 squares the entire product including pills — which is what Swiss, Terminal, Editorial and Blueprint all need.
--i-density scalar1 Multiplies the whole spacing ramp.
--i-type-scale scalar1 Multiplies the whole type ramp — the counterpart to density, which scales space. Both levers or neither: a dense theme that only tightened spacing ended up with cramped gaps around house-sized type, which reads as broken rather than dense.
--x-rule-w scalar1px Weight of the primary separator, and of every outline the surface modes draw.
--x-grid modenone · columns · fine A background grid painted on the stage, behind everything. --x-grid-line and --x-grid-size let a theme set the colour and pitch without owning the geometry.
--x-annotate mode0 · 1 Item numbers on rows, stats and cards. Implemented as CSS counters so no component has to know its own index — and the reason that is worth stating: making each stat a query container silently broke it, because container-type implies style containment, which scopes counters. Every item numbered 01, with a green build. Only the pixels showed it.
--x-hover modelift · mark · invert What a control does on hover. A control must always announce itself; themes disagree about how. invert reads --x-select-bg and --x-select-fg — it was hardwired to a wash with no foreground token, which is not an inversion, and a mode the contract names has to be a mode it delivers.
--x-section-rule modenone · trailing A hairline running out from a section label to the end of the measure. Under rule and none surfaces every boundary is gone and a bare label separates regions weakly; three themes wanted this independently.
--x-band modenone · rows Zebra banding on dense tables — how a ledger stays trackable once nothing draws a box.
--x-leader mode0 · 1 The magazine-index device: a dotted run from a row's title to its meta, so the eye tracks across a wide row without a rule under it.
--x-emphasis modewash · fill How the primary control carries emphasis. Outline-plus-wash was the only emphasis the system could express, so a theme whose primary button is a solid block of ink with the page punched out of it had to write that as a per-theme rule.

Scalar or mode? A size, weight or colour is a --x- custom property — cheap, so prefer it. A discrete choice that changes rules is a data-* attribute written by applyTheme(). Modes cost more, and a mode with two values probably wants to be a scalar instead.

Watch for coupling before adding a knob. The figure and the stat floor were the cautionary case: the fix was not a third token to tune, it was deriving the figure from its own container so the two can no longer desync. Prefer deriving over adding.

Adding a theme

Two files: src/themes/<id>.css for the tokens, and one object in src/themes.js for the structure. They are split because they are enforced by different machinery — tokens are cascade, modes are attributes — and because applyTheme() writing every mode in one pass is what makes a half-applied theme impossible. Then the import goes into src/instrument.css, and nothing else in the product changes.

The full procedure — the registry fields, the roles a theme must fill, the contrast bar, the rule about never targeting an app class, and what to do when your theme file starts growing rules instead of tokens — lives in AUTHORING.md, alongside adding a component, a shell variant, and a structure axis. It is not repeated here; one copy is the point.

The one line worth carrying out of it: if a theme file is accumulating rules that restate the same idea per selector, or two themes independently wrote the same override, that is the contract missing an axis — and an axis with no consumer is speculation, so use it in at least one theme before you ship it.

The build passing is not evidence the UI is right. Open the gallery and step through every theme; some of these bugs compile perfectly.
