Composed examples

index.html shows the parts one at a time. This page shows them assembled, because most of what goes wrong in a design system goes wrong between components rather than inside one: a screen that reads flat, a state that looks like a different state, a table that stops being scannable when a theme tightens the spacing. Everything below is library classes and nothing else — where a rule on this page is scaffolding rather than system, it says so and says why.

The same screen, four surfaces

Surface is the axis that decides whether the product is made of boxes. It is not a colour and not a variant prop: it is one attribute on the document, and the four modes are written once in contract.css against the component layer, so no component knows which one is running and no theme has to restate them. tile is a filled plane, a hairline and a radius — the default, and Bento's. outline drops the fill for a hard square edge; that is Blueprint's drawing-office register. rule deletes the box entirely and leaves a top rule and whitespace, which is where Swiss and Editorial live. none leaves neither: density and alignment do all the dividing, and that is Terminal.

Surface is a decision about the document, not about a region, which is why it is an attribute on <html> and not a prop. The four panes below cheat: they scope that attribute to a wrapper, which works only because the modes are descendant rules. It is a one-way cheat — a pane can add a mode to its own subtree but cannot subtract the page's, and where the page's own mode is written later in contract.css than a pane's, the page still wins inside the pane. So under Blueprint, Instrument and Bento all four panes are distinct; under Swiss or Editorial the outline pane collapses into rule, and under Terminal both collapse into none. That is the system telling you something true rather than the demo failing. To see one mode carried across a real screen, set the surface override in the top bar and scroll back up — it rewrites the document attribute, which is the only honest way to ask this question.

Identical markup in each pane. What is worth watching is that the tags, the callout and the trace rail are unchanged across all four — the mode list names six classes (panel, card, row, stat, finding, loaderror) and nothing else. A verdict, a rail and a run of verbatim output are content rather than containers, so they keep their drawing everywhere. The corollary is the rule in AUTHORING: a new component that draws its own box must either wear one of those six classes or be added to all four mode blocks. That is not pedantry — the surface used to be hand-written on six classes while the mode blocks listed only four of them, so on every non-tile theme findings and load errors kept a filled rounded tile beside square outlined panels, and on Terminal they were the only boxes left on screen.

A form

Every control is the same two classes: i-field for the label-and-control column, i-input for the control itself, whether that control is a text box, a textarea or a select. One class rather than three is what keeps the control voice identical when a theme changes the chrome face — the same reason the theme picker in this page's own top bar is an i-input. Pills are a choice you can see all of at once; a select is a choice you cannot. The well underneath is recessed rather than raised because it holds verbatim machine output, and the toolbar's status line is the one place a form is allowed to talk back in italics.

Two details worth stealing. The focus ring is a real :focus-visible outline in the signal colour with an offset, never a removed outline — a keyboard user has to be able to find the control they are on. And the library states box-sizing: border-box for every i-* element rather than assuming the host page has a reset: without it, any control that carries both an explicit width and padding overflows its parent by exactly padding plus border, which is how a chat composer's textarea once slid underneath its own Send button.

An agent run

The shape every agentic surface in this product converges on: what the machine did, what the gate decided, what the review found, and one line of terminal verdict. The 2px rail down the trace is the system saying a machine did this — the middle of three border weights that each mean something (1px is a boundary, 2px is a rail or a spine, 3px is the identity stripe on the rows above). Depth is translucency, a hairline and the page wash showing through; the system draws no shadow for it, which is why it stays crisp in dark mode instead of turning to mud.

Nothing here animates. The motion budget forbids it on a hot path, and trace lines and table rows are the definition of one: they arrive while you are reading them. The tile-arrival animation that i-stats and i-cards get on first paint is deliberately not applied to i-tr or i-traceline for exactly that reason. And prefers-reduced-motion does not mean "turn it all off" — travel and scale go, opacity stays, because removing every transition removes the signal that something arrived, which is what a motion-sensitive reader still needs.

Empty, failed, loading

Three states that a screen must never be allowed to invent for itself, shown together because the only way to check them is side by side. A failed fetch must never look like "none". On a runs list the difference is mild; on a security screen those two are opposite meanings — "this host has no open findings" and "we could not ask the host" would be the same picture, and one of them is an all-clear you have not earned. So the load error says what it could not reach, says in as many words that this is not the same as it being empty, and offers the retry. The empty state is centred in a capped column with margin-inline: auto, because a capped column pinned to the left of a full-width panel with its own text centred reads as a layout bug rather than as an empty state.

No runs yet

Talk to an agent in Chat — each gated run is metered here.

failed — we could not ask

Couldn't reach the runs store

It may be starting, or unavailable. This is not the same as it being empty.

loading — we are still asking

Loading the run ledger…

Loading is one dim line of prose and that is the entire component — no skeleton, no spinner. The distinction that costs something is empty versus failed, and that is where the layout goes.

Density

The same ledger at --i-density 0.8, 1 and 1.25. Density is one multiplier over the whole spacing ramp, so every gap and padding in every component moves together from a single number, and a theme opts in with one declaration. Its counterpart is --i-type-scale, which multiplies the type ramp — and the reason both exist is that one alone is a trap. A theme that tightened only the spacing ended up with house-sized type sitting in cramped gaps, which reads as broken rather than dense; Terminal now moves both at 0.74 together. These three panes move space only, which is exactly the half-lever that was the bug — the text is the same size in all three, and you can feel it in the widest one.

Composition rules

Four rules that decide what may join the system and how it has to behave once it is in. They are the reason nine screens render correctly in six themes with no screen knowing which theme is running.

Admission

Three screens, or a real cost

A pattern earns a component when it has appeared in three screens, or when getting it wrong carries a real cost — a metric that is silently unclickable, a verdict that reads green when it failed. Two occurrences stay a one-off in the consuming app until they prove themselves. Everything in the compound layer was extracted from working screens rather than designed up front, and the ordering is the point: a library designed in advance guesses at what screens need, one extracted from them knows. Card exists because the Home launcher, the workflow catalog and the fleet host list had independently grown the same shape at three different paddings.

Colour

Tone is a meaning, not a colour

The five tones are claims: signal (this wants you, or binds you), machine (the system is speaking), crit, ok, mute. A prop asking for "amber" is a prop that has not decided what it means. A theme picks the hue; it never repurposes the role — --i-crit is "this failed" in every theme, forever, which is the single rule that lets six themes swap without auditing every screen. Hues are the scarce resource, so emphasis rides on a second channel instead: fill weight, an outline, a ring, a rail, a stripe, a glyph. Adding a hue needs a changelog note; adding a channel usually does not.

State

State is is-*

is-on, is-link, is-hot, is-refuted. Never active, never selected — one prefix means you can read a class list and know instantly which parts are identity and which are condition. Its sibling rule: anything that does something is a <button>. A div with a click handler is a keyboard trap, which is why every clickable stat, card and row on this page is a real button carrying is-link.

Surface

It has to survive all four modes

A component is not finished until it renders correctly under tile, outline, rule and none. A hard-coded border looks wrong in Terminal and Blueprint and nobody will know why. Use the shared surface classes or add yours to the four mode blocks — and then look at it, in more than one theme, because passing the checks is not evidence the UI is right. Two bugs in this repo compiled and linted cleanly and were wrong on screen: a container-type added to fix a figure overflow silently scoped the CSS counters that drive annotation, so every numbered item read 01; and a display: flex overrode the browser's own dialog:not([open]) { display: none }, so every drawer in the app rendered permanently. Both are why the query container now sits one level in, on i-stat-fit, and why the figure is min(--x-figure, 18cqi) — sized against the column it actually got rather than against a number a theme hoped would fit.
